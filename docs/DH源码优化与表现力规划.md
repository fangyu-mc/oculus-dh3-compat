# DH 3.2.0-b 源码优化与表现力规划

日期：2026-09-21。状态：源码初审与实施规划，未修改运行代码，未实测性能收益。

## 1. 目标与路线

面向整合包的广大玩家，减少 CPU、GPU、内存、显存和磁盘开销，同时保持或提升远景表现。优先改善帧时间长尾和飞行连续性，其次提升稳定帧率与可承载景物复杂度。配置调低不算源码优化成果。

主路线：保留 DH 数据与世界生成体系，修复 Oculus 接入，优化 DH 热路径；在测量证明有必要后，增加可选的批量绘制和 GPU 遮挡后端。暂不整体移植 Voxy，不同时推进 DH 3.3 升级。各阶段独立开关、可回退，避免把所有玩家绑到高版本 OpenGL 扩展上。

“极致”以实测收益、画质与兼容性共同判定，不意味着无限线程、无限缓存或强制最高 GPU 特性。

### 已核实的渲染细节

- DH `common/.../render/openGl/terrain/GlDhTerrainShaderProgram.java` 的 `render()`：逐容器设置 model offset、绑定程序、发出 `DhApiBeforeBufferRenderEvent`；逐 VBO 获取 VBO/IBO 读锁、绑定、`glDrawElements`、解绑。存在值得测量的调用与同步成本，但尚未证明它是实际主瓶颈。
- DH `GLBuffer.java` 已支持多种上传方式，且包含平台特定的大上传分片处理。不能把“增加 buffer storage”当作全新优化，也不能删除已有驱动规避措施来追求漂亮数据。
- Oculus `DHCompat.java` 已在接入时关闭 DH 自带 AO/雾并延后透明渲染；不能重复申报“关闭双重 AO/雾”的收益。
- Oculus `DHCompat.copyOpaqueDepth()` 保存不含透明物的深度，不能为少一次复制而破坏水体/光影采样语义。
- Oculus `MixinDHShadowPassGuard` 跳过阴影期间的 DH 渲染，并在 DH 光影接入生效时跳过原版淡入淡出。属于当前功能边界，是否造成用户可见缺陷需实景确认。
- Voxy 的 `MDICSectionRenderer` 使用间接批量绘制；`HierarchicalOcclusionTraverser`、HiZ 与计算着色器构成 GPU 层级可见性路径；`UploadStream` 使用持久映射、批量复制和 fence 回收。
- Voxy `UploadStream` 在分配失败路径仍会 `glFinish()`，说明先进架构也存在压力下的同步风险，不能照搬整个实现。
- Voxy `WorldSection` 使用 32×32×32 三维块与层级数据，配合模型烘焙和纹理体系。其视觉效果不是一个渲染参数带来的；用 DH 现有数据能保留哪些细节，必须独立验证。
- 本地 Voxy `LICENSE.md` 写明 All rights reserved / Do not redistribute。采用公开通用算法自主实现；直接复用代码进入分发前必须有相应授权依据。

## 3. 分阶段实施

### P0：建立可重复的证据链

1. 补齐 3.2.0-b 发布对应的 coreSubProjects 提交，记录父仓库/子模块 SHA、jar SHA256、依赖与 JDK。禁止用核心仓库最新 main 冒充 3.2.0-b。
2. 建立独立的 DH 优化扩展模块（暂名 dh-performance-compat），负责 DH Mixin、遥测、功能开关；Oculus shader、FBO、uniform 和生命周期修复留在 oculus-dh-compat。不向 fyaoa 堆叠渲染后端代码。
3. 统计各阶段 CPU 时间、GPU 时间、绘制次数、面数、每帧上传字节、等待时间、队列长度、缓存命中率、堆/堆外/可测显存和 I/O；GPU 查询延迟读取，禁止为了计时每帧同步等待 GPU。
4. 区分冷缓存导入、热缓存静态渲染、高速移动、后台世界生成四类负载。固定种子、视点、路线、分辨率、光影和质量设置，重复采样报告中位结果与波动。
5. 先形成热点排名和缺陷复现清单，再确定下一阶段每项优化的投入顺序。

交付：可复现基线、低开销诊断开关、版本清单、可回退构建。未补齐核心源码前仍可审计和测量现有 Oculus/GL 渲染路径。

### P1：先修正确性与生命周期

重点覆盖：透明水面深度、不透明深度快照、FBO 附件尺寸/格式、程序切换、GL 状态恢复、切维度/切光影/改窗口尺寸后的重建与释放。

- 画出实际 pass 顺序与深度纹理读写关系，确定每张深度纹理的坐标、投影和透明语义。
- 审计无 dh_terrain、无 dh_water、关闭光影、DH 缺席时的回退和清理。
- 用调试视图定位交界缝隙、重影、深度闪烁、远近水体不连续；证明问题所属阶段后局部修复。
- 单独处理淡入淡出与远景投影阴影：现有 guard 不能简单删除，必须先有兼容的替代路径。

交付：每个缺陷都有复现、修复前后截图/录像和性能对照。不得通过大雾、隐藏地形或关闭透明掩盖问题。

### P2：面向全部玩家的 CPU、内存与 I/O 优化

核心源码补齐后逐项审计；以下为候选，不是假定 DH 尚未实现。

- **调度与背压**：去重同一区域更新，合并短时间脏数据；近处可见任务优先，兼顾等待时长防止饥饿；切维度/离开范围取消过期工作；为生成、转换、构网格、上传设置有界队列和预算，防止后台任务淹没前台。
- **世界读取安全**：保留 MC/Forge 对线程的要求，适合时在安全线程获取快照；不把区块对象直接交给任意线程，也不破坏 TerraForged 的生成语义。
- **网格与分配**：定位重复转换、邻居查询、临时对象及原生缓冲分配；按块版本缓存结果、批量处理脏区、复用有上限的缓冲。合面必须保留材质、光照、透明与纹理边界。
- **缓存与存储**：区分数据缓存和可重建网格缓存，按实际字节限制；测量数据库锁、压缩和事务批量的收益。初期保持现有数据库格式，避免为了存储重写引入存档迁移。
- **资源竞争**：控制单人集成服与客户端后台任务总压力，依据帧时间与队列反馈调节后台吞吐；不能仅按逻辑核心数创建大量线程。

交付：保持相同视觉质量的飞行/加载帧时间改善、内存峰值改善；同时记录加载完成时间，防止靠无限延迟工作制造流畅假象。

### P3：降低渲染线程与驱动提交开销

由低风险到高风险推进：

1. 对逐 LOD/VBO 的绑定、uniform、锁等待和事件派发分别计时。只有在自身控制的作用域内缓存 GL 状态，跨模组事件边界不得假定状态不变。
2. 验证共享索引、批量回收、缓冲分配与上传预算；保留资源生命周期保护，不能直接删锁。采用不可变渲染快照、代际标记和延迟销毁时明确所有权。
3. 原型验证共享几何缓冲与 multi-draw：先实现不透明批次，再处理透明排序；每个 draw 的位移/材质输入须适配，不能只是把 glDrawElements 换成一个新函数。
4. shader override 与逐缓冲事件是批处理兼容障碍。仅对已验证支持的管线启用批处理；有逐缓冲状态修改时保留原路径，不能跳过事件改变 API 行为。
5. 能力满足时评估持久映射 staging、fence 轮转与上传背压。缓冲满时优先延后上传、继续显示旧数据，不在正常帧路径调用 glFinish，也不覆盖 GPU 尚在使用的内存。

交付：CPU 提交与驱动开销下降、上传尖峰下降；老后端可一键回退，透明顺序不退化。

### P4：可选的 GPU 遮挡与 LOD 后端

这是较高投入的性能上限项目，在 P0–P3 证明剩余瓶颈后进入。

- 不透明渲染评估 Hi-Z 层级遮挡，避免山体后方大量不可见几何与像素着色。平原/海面遮挡少时可能不划算，保留绕过路径。
- 深度来自哪个 pass、投影是否相同、反向 Z/精度、视口与近裁剪处理必须明确；不可把 MC 近景和 DH 远景深度直接混用比较。
- 转身、传送、相机穿越遮挡体时使历史结果失效；保守扩大可见集合。时间相干优化不能带来山体突然消失。
- 避免同步读取可见性结果；能力充分时再组合 GPU 命令生成与间接绘制。
- 以屏幕误差衡量细化程度，加入滞回和父子 LOD 原子替换；子节点未就绪时继续渲染父节点，避免洞和反复跳级。
- 透明物单独处理，不能直接作为可靠遮挡体；不得破坏其排序。

交付：复杂遮挡场景的 GPU/CPU 收益、无遮挡场景的成本上限、AMD/NVIDIA/Intel 实机兼容验证。基础后端不依赖此功能。

### P5：在省下的预算内提升表现力

- 优先保住山体轮廓、悬崖、天窗、洞口、水岸和大型结构，而不是均匀堆积远景面数。
- 近远交界：尺度一致的纹理与群系色、光照连续、稳定抖动/过渡，兼顾光影 TAA，避免噪点和拖影。
- 纹理：审计现有 textured LOD 的取样、mipmap、图集边缘和重复纹理摩尔纹，先改善已有体系。
- 透明：水位、深度、雾、折射采样与远近衔接；不使用全距离高成本透明策略。
- 阴影：独立预算与距离，验证光影包契约后再增加 DH 投影阴影；不把完整远景重复绘入每级阴影。
- 特殊维度：deeplands 巨洞、荒芜峡谷天窗、传说维度巨山与雨林。验证现有洞穴剔除假设，避免把可见洞穴误当作隐藏地形。
- 若缺失细节已在 DH 数据简化中丢失，明确这是数据/网格表示问题；后处理无法恢复。三维体素层或新数据格式作为后续独立研究，不伪装成小补丁。

## 4. 验收矩阵与合入标准

硬件至少覆盖：低功耗/核显、主流独显、较强独显；AMD/NVIDIA/Intel 驱动分别抽样。能力按实际 GL 扩展和验证结果判断，不按显卡品牌一刀切。内存/显存受限场景单独测试。

场景至少覆盖：热缓存静止、快速转身、高速飞行、冷缓存生成、大海透明、复杂山体遮挡、巨洞、切维度、切光影、资源重载、窗口尺寸变化、长时间往返。测试无光影、Complementary 主样本、其他兼容 DH 光影样本和无 DH 程序的回退。

指标：CPU/GPU 分段耗时、帧时间 P50/P95/P99、超过 33/50/100 ms 的帧数、加载可见区域完成时间、驻留/峰值内存、上传量、绘制量、后台生成吞吐；单人游戏记录服务端 tick 时间。显存不可可靠查询时明确标记，不能伪造跨厂商准确统计。

建议准入门槛（待基线确认后冻结）：相同画质下目标瓶颈改善超过测量噪声，通常争取至少 10%；其他常用场景 P95/P99 不产生可重复的明显退化。大型后端若没有足够收益覆盖维护成本则不默认启用。不得以降低实际有效视距、拖慢加载或丢细节作为未披露的优化。

帧率改善和画质提升分开做 A/B，再测试组合。每项变更单独开关，建立“原版 DH + 当前 Oculus”“仅修复”“单项优化”“组合优化”四组对照。

每次实现按模块构建，部署匹配 jar 并核对哈希；实际验证通过后再纳入整合包。规划阶段不改配置、不替换 jar、不承诺未经测量的帧率倍数。

## 5. 第一轮工作包与决策点

第一轮只做：补齐匹配核心源码与版本证据 → 增加分段测量 → 固定路线基线 → 审计 Oculus 深度/pass/生命周期 → 对实际最高成本做一个独立优化原型。

优先原型候选为逐 VBO 提交成本与上传尖峰；如果测量显示主要成本来自世界生成、网格或透明像素，则依热点调整，不为了对标 Voxy 强行上 GPU 架构。

第一轮交付后决定：继续传统 DH 热路径优化，还是进入共享缓冲/批量绘制，再由收益决定是否值得引入 GPU 遮挡。全流程以实际可见质量和广泛硬件的帧时间为依据。
